# Описание работы RAG-подхода (Высокоуровневая архитектура)

Система **Astana Walk AI** построена по принципу **Zero-Hallucination Geosemantical RAG**: языковая модель никогда не придумывает точки интереса из своей памяти, а работает исключительно как интеллектуальный ранжировщик, планировщик и объясняющий слой поверх проверенных кандидатов из гео-индекса.

## 1. Конвейер обработки запроса (5 этапов)

```
[Запрос пользователя + Локация + Контекст]
        │
        ▼
Этап 1. Query Intent & Privacy Gate (backend/retrieval/intent.py, geo.py)
  • Округление координат до ~100 м (`round_coords`, 3 знака) — сырой GPS нигде не хранится.
  • Авто-распознавание якорных ориентиров из текста («возле Mega Silk Way», «у Экспо 2017», «у Байтерека»).
  • Извлечение бюджета времени (`30–60 мин` → 60 мин, `1–2 часа` → 120 мин), погоды (`cold_windy`),
    потребности в безбарьерной среде (`wheelchair`) и языка (`ru` / `kk` / `en`).
        │
        ▼
Этап 2. Гибридный гео-семантический поиск (backend/retrieval/chroma_retriever.py, hybrid_bm25.py)
  • Гео-префильтр по bounding box + точный отсев по формуле гаверсинуса (`haversine_m <= max_distance_m`).
  • Семантическая близость: мультиязычные эмбеддинги `paraphrase-multilingual-MiniLM-L12-v2` в ChromaDB
    по обогащённым документам POI (название + категория + русские/английские синонимы тегов).
  • Лексический буст (Okapi BM25 + `QUERY_TAG_HINTS` + точное совпадение имени POI):
    гарантирует, что жёсткие требования («розетка/wi-fi», «коляска», «халяль», «казахская кухня», «футбол»)
    не размываются векторным поиском.
        │
        ▼
Этап 3. Проверка режима работы и контекстный реранкинг (backend/retrieval/hours.py, recommender.py)
  • Парсинг `opening_hours` из OSM в часовом поясе Астаны (UTC+5): поддержка `24/7`, дней недели,
    ночных переходов (`18:00-02:00`) и перерывов.
  • Проверка окна визита (`check_visit_window`): учитывает не только текущий момент, но и не закроется ли
    заведение за время `walk_min + visit_min`.
  • Честная шкала уверенности: `confirmed_open`, `likely_open` (до закрытия ≤30 мин),
    `unknown` (часы не указаны у 66% POI в OSM — система никогда не пишет «открыто!»), `likely_closed` (штраф −0.30).
  • Погодная и временная адаптация: при ветре/морозе Астаны повышаются места с тегом `indoor`;
    при бюджете времени проверяется условие `2 * walk_min + visit_min <= time_budget_min`.
        │
        ▼
Этап 4. Построение связанного микро-маршрута (backend/retrieval/route_planner.py)
  • Вместо 3 разрозненных радиальных лучей от пользователя строится последовательная цепочка из 2–3 точек:
    `Старт (rounded_100m) → Точка 1 (Прогулка/Осмотр) → Точка 2 (Культура/Экспозиция) → Точка 3 (Кофе/Отдых)`.
  • Оптимизируется разнообразие категорий, длина переходов между соседними точками и суммарный бюджет времени.
        │
        ▼
Этап 5. Генерация с защитой от галлюцинаций (backend/generation/prompts.py, recommender.py)
  • В промпт LLM (OpenRouter API) передаются ТОЛЬКО округлённый контекст и список кандидатов с предрассчитанными
    расстояниями (точные координаты пользователя в LLM не отправляются).
  • Пост-валидация: каждый `poi_id` в ответе LLM проверяется через `get_poi(poi_id)` и список кандидатов retrieval.
    Любой выдуманный `poi_id` мгновенно отбрасывается, а дистанция и `open_status` перезаписываются эталонными
    значениями из поискового слоя.
  • Если API-ключ не задан или сеть недоступна на демо, автоматически включается детерминированный генератор
    (`smart_fallback`), обеспечивающий 100% отказоустойчивость на защите.
```

## 2. Формула ранжирования кандидатов

На этапе поиска каждый объект внутри радиуса `max_distance_m` получает базовый композитный скор:

$$\text{Score} = 0.65 \cdot \text{Relevance} + 0.25 \cdot \left(1 - \frac{d}{D_{\max}}\right) + \Delta_{\text{hours}} + \Delta_{\text{hint}} + \Delta_{\text{context}}$$

где:
- $\text{Relevance} \in [0, 1]$ — гибридная семантическая и лексическая близость с бустом за совпадение целевых тегов (`TAG_BOOST = +0.15` до 2 тегов) и точное имя POI;
- $\Delta_{\text{hours}}$ — поправка на статус работы (`+0.10` для `confirmed_open`, `+0.05` для `likely_open`, `0.0` для `unknown`, `-0.30` для `likely_closed`);
- $\Delta_{\text{hint}} = +0.15$ — бонус за выполнение явного требования пользователя (`wifi`, `wheelchair`, `landmark`, `cuisine_kazakh`);
- $\Delta_{\text{context}}$ — контекстная поправка (соответствие бюджету времени, тег `indoor` при плохих погодных условиях в Астане, ночная безопасность).

## 3. Честное разделение фактов и генерации (`poi_data` vs `generated_idea`)

Одно из главных требований жюри — прозрачность источника каждой рекомендации:
- **`poi_data` (Факты из базы POI):** название, категория, подтверждённые теги OSM (`wifi`, `wheelchair`, `indoor`, `landmark`), расстояние по формуле гаверсинуса, время пешком (с коэффициентом уличной сети $1.3$ при скорости $4.5$ км/ч) и разобранная строка `opening_hours`.
- **`generated_idea` (Идея и план модели):** мотивация «почему стоит зайти», микро-план «что делать там» и любые предположения об атмосфере или деталях, не размеченных в OSM (например, наличие свободных розеток у столика, когда в OSM указан только тег `wifi`).
